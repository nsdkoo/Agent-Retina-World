### 09-30 · 差异化第二步：后果预演（预判）

- **做了什么**：新增 `agent/foresight.py`。在**要用户拍板**的动作执行前，算出
  「这一步会做什么、能不能撤销、有什么风险」，拼进挂起提示。
- **为什么**：传统桌面 agent 是**纯反应式**的——看到 → 点下去 → 发现错了。
  而桌面场景最痛的地方恰恰是**很多操作不可逆**：关掉没保存的文档、删了文件、
  发出去了消息，点下去就收不回。人类不这样干活，人点删除前会想一下。
- **为什么只做文本级**：对标 ICLR 2026 的 CUWM（arXiv 2602.17365）。它把预测拆成
  文本 + 视觉两阶段，但**论文自己的实测结论**是：① 结构清晰度比像素保真度更重要
  ② **文本+图像同时给反而降性能**（跨模态冲突）。结论：对决策有用的部分几乎全在文本里，
  训图像模型是几个数量级的成本换接近零的决策收益。
- **两级策略**：规则版打底（永远可用、离线、可解释），LLM 版仅在不可逆时启用。
  **预演本身不能成为新的故障点**——任何异常都退回规则版。
- **只在该做的地方做**：预演只在挂起时触发。对只读动作预演纯属浪费，
  还会稀释真正该看的提示。
- **踩坑**：初版可逆性判断**只看 risk 等级**，把 `files.move`（有 undo）、
  `files.delete`（走回收站）误报成危险动作。提示一多用户就疲劳，真正危险的反被忽略。
  改成 `ToolSpec.reversible` 让工具自己声明，优先级：显式声明 > 只读/幂等 > 默认不可逆。
- **涉及**：`agent/foresight.py`（新）、`agent/controller.py`、`tools/registry.py`、
  `tools/registry_setup.py`
- **commit**：`5db4373`

### 09-30 · 差异化第三步：主动准备

- **做了什么**：新增 `proactive/prepare.py`。在用户空闲时提出**具体**能帮的事——
  未完成的意图 / 中断的任务 / 从习惯推断的下一步。
- **为什么**：`proactive/` 原来只有三个**报告生成**方法（日报/待办/时间线），
  本质是「你问它才答」。
- **核心设计：主动 ≠ 打扰**。三条缺一不可：知道有什么事值得做、知道现在是不是时候、
  **说得出具体做什么**。第三条最容易忽略——含糊的建议等于把决策成本推回给用户，
  那还不如不说。所以 `interruptible=False` 时直接闭嘴。
- **时机门控是开关不是优化**：`interruptible` 来自 `SightEvent`——
  项目本来就在采集「此刻能不能打扰」，主动机制只是把它用起来。
- **依赖前两步**：`habit` 那一路的原材料是 episode 的 `evidence_paths`，
  也就是第一步特意补上的「动过的路径」。**没有第一步，这一步无从谈起。**
  `resume` 建议直接给 `resume_from:<task_id>`，接上更早做的续跑能力。
- **涉及**：`proactive/prepare.py`（新）、`proactive/__init__.py`
- **commit**：`6c28916`

### 三级跳的贯通关系

```
① 懂你 ──────────→ ② 预判 ──────────→ ③ 主动
知道你怎么干         知道做了会怎样        在合适时候提出下一步
   │                    │                    │
   └── episode 记 resources ─────────────────┘
                        └─ 预演只在挂起时触发
```

**三者不是并列的三个功能，是一条链**：① 让 agent 有「记忆」，② 用「记忆 + 动作」
推演后果，③ 在合适时机把前两步的结论变成建议。

### 09-30 · 把预判与主动接进运行时和 UI

- **做了什么**：收掉三级跳的两条尾巴。
  - ② 的 LLM 版：`build_agent` 里构造 `ForesightEngine(llm_predict=...)`
  - ③ 接 UI：`VoiceAssistant` 新增 `on_suggestion` 通道，用气泡展示建议
- **为什么 ② 值得走一次模型调用**：规则版能准确说出「做了什么」（工具自己最清楚），
  但说不出「**在当前这个屏幕上**做了之后到底会怎样」——那需要看上下文。
  而这类动作**天然频率很低**（只在不可逆时触发），成本可控。
- **③ 的时机门控抽成了纯函数** `should_speak_now`：**抽出来是为了能被直接测** ——
  这是整套机制里最该守住的地方。它做坏了**不会报错**，
  只会让用户默默把通知关掉，而你还以为一切正常。
- **四道门槛**：不忙 / 不在会话中 / 距上次够久 / 真有可说的事。
- **两个克制的细节**：
  - 主动建议**刻意不加语音播报** —— 主动说的话如果还念出来会很吵，文字扫一眼就够
  - 计时**只在真有话说时才更新** —— 否则「没内容」也会把时钟推后，下次真有事反而提不出来
- **顺序不能反**：watcher 回调从 `journal.record` 换成 `_on_sight`，
  **先记日志再看要不要提建议**。记日志是主线（数据飞轮、日报都靠它），
  建议是锦上添花，绝不能影响记录。

### 09-30 · 建议可一键执行（补上「主动」闭环的最后一环）

- **做了什么**：`Suggestion` 加结构化 `action`；`VoiceAssistant.run_suggestion` 做分发；
  气泡支持**按条指定**点击回调。
- **为什么**：建议原本只能在气泡里看 —— 用户看到「接着做「跑评测黄金集」」
  还得自己开口说一遍。`resume_from` 的钩子早就备好了，缺的只是点击回调。
- **关键区分**：**提示只能看，建议点一下就能动手**。所以 action 用结构化 dict
  而不是拼自然语言 —— 动作最终要按下标参数调用真实方法（`resume_from(task_id)`），
  拼字符串再解析回来是绕远路，还容易解析错。
- **最要紧的一条：主动建议不是特权通道**。续跑走 `controller.resume_from`
  （那里照常判权限、照常挂起等确认），意图和习惯走 `handle_command` 常规路径。
  **这样「主动」就不会变成「绕过审批」的借口 —— 主动不等于自作主张。**
- **气泡改造**：`show_message` 加可选 `on_click`，按条指定而非全局固定。
  原来气泡的点击语义只有一种（开面板），但建议需要「点一下就去执行」，
  混用一个回调会让用户点哪儿都做同一件事。

### 09-30 · 预演结论进 UI + 建议条数提示

- **做了什么**：盘查接线缺口时发现 —— `foresight` 数据发到了 EventStream，
  但 **voice 层没人消费**，预演只在挂起提示的文字里出现，UI 上完全看不见。
  - `VoiceAssistant` 新增第五条通道 `on_foresight`
  - `toast` 加 `Warn` 样式（light / dark 各一套）
  - 气泡加「还有 N 条」提示
- **为什么单独一条路**：预演它是**警示**不是进度。混进 progress 里，
  用户会把「这一步收不回来」当成「正在执行第 2 步」，扫一眼就划过去 ——
  **那这一层就白做了**。
- **配色为什么不用正红**：正红在浅色桌面上太刺眼，看两次就想关掉提醒。
  用暖橙红，既读得出「注意」，又不至于让人烦。
  `Info` 和 `Warn` 也刻意分开 —— 把「顺手提一句」和「这一步收不回来」
  做成同一个样式，用户会把两者都当可忽略的提示。
- **只有不可逆的才弹**：可逆动作不弹警示。弹了就人人都是警告，
  用户对警告脱敏，真正危险的那次反而被忽略 —— 狼来了的道理。
- **涉及**：`voice/assistant.py`、`voice/ui_qt/toast.py`、
  `voice/ui_qt/signals.py`、`voice/ui_qt/ball.py`

### 09-30 · 面板里的建议也能点执行

- **做了什么**：上一轮只做了气泡可点，面板里还是纯文字。补上——两条入口都能点。
- **为什么**：面板才是「**回头看的地方**」。用户在那儿看到「接着做 X」却点不动，
  说不通。
- **自绘列表怎么处理点击**：`MessageView` 是 `QListView` + 自绘 delegate，
  **delegate 只管画不管点**。所以要自己在 `mousePressEvent` 里用 `indexAt`
  定位命中了哪一行，再问 model 这一行有没有 action。**只处理左键** ——
  右键要留给列表自己的行为。
- **存结构化 action 而非拼字符串**：model 加 `ACTION_ROLE` 存 dict。
  动作最终要按下标参数调真实方法（`resume_from(task_id)`），拼成文本再解析是绕远路。
- **`run_suggestion` 同时接受对象和 dict**：气泡直接传 `Suggestion` 对象，
  面板要经 UI 序列化再传回来。**只认一种形状的话，面板里的点击会静默失效** ——
  正是上一轮那类「不会报错、只是不生效」的坑。
- **入口不同、路径相同**（要紧的约束）：面板点击走 `_run_action` → `run_suggestion`
  → 照常过权限审批，和气泡完全同一条路。**不因为入口不同就开小门** ——
  主动建议不是特权通道。
- **涉及**：`voice/ui_qt/messages.py`、`voice/ui_qt/panel.py`、`voice/ui_qt/ball.py`、
  `voice/assistant.py`
