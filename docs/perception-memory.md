# 感知记忆设计

目标一句话：**你在电脑上做了什么，它自己看着记下来，不用你告诉它。**

## 为什么不走「定时截图 + 看图模型」

老路子是每 N 秒截一张图丢给视觉模型识别。三个问题：

| 问题 | 具体表现 |
| --- | --- |
| 白拍 | 你盯着同一个页面五分钟，它拍十张几乎一样的图，还都送模型 |
| 花钱 | 一张图一次视觉推理，一天下来是笔真金白银 |
| 不准 | 识别出来的文字会有错——`l` 认成 `1`、中文串行，事后搜不到 |

Screenpipe 给的答案是 **accessibility-first**：先问操作系统「屏幕上有什么」，
拿不到才退回 OCR。Windows 上就是 UI Automation（读屏软件用的那套）。

## 三层采集

便宜的在前面，贵的在后面：

```
1. 窗口标题 + 进程名     每次都给，几乎零成本
2. UIA 结构化文本        只在窗口切换时调一次（实测约 1.4 秒 / 200 条文本）
3. 截图                  默认不拍；UIA 拿不到内容的应用（游戏、远程桌面）才考虑
```

**关键在触发时机**：不是定时轮询，而是**前台窗口变了才采**。这带来两个好处——
CPU 只在切换那一瞬间动一下，其余时间完全安静；而且记录下来的天然是「事件」，
不是「帧」。事后回忆时想知道的恰恰是「我什么时候从 A 切到了 B」。

```
capture/watcher.py   DesktopWatcher   轮询前台，只在切换时产出 SightEvent
capture/uia.py       read_foreground_text   PowerShell + .NET UIAutomationClient
```

UIA 走 PowerShell 而不是 ctypes 重写 COM 接口：Windows 上零依赖，代码短到能一眼看完，
一次几百毫秒的开销摊在「窗口切换」这个动作上完全划算。

## 前台不够用：为什么要记「整桌窗口」

只记前台会丢掉最关键的信息。真实工作时桌面上同时开着浏览器、编辑器、文档、聊天窗口，
而「他在忙什么」往往写在这些窗口标题里——`淘保函 - Google Chrome`、
`客诉方案.pptx`、`25年5月业绩分配.pdf`。

所以每条观察除了前台窗口，还会附上**同屏所有可见窗口的标题**，一起进全文索引。
效果是：即使你当前焦点在知乎，搜「淘保函」也能找回那一刻。

```
前台：知乎（Edge）+ 200 条页面文本
同屏：WorkBuddy、淘保函 - Google Chrome、QQ、微信、PowerShell
```

## UIA 的边界：谁读得到、谁读不到

实测下来分两类：

| 类型 | 例子 | UIA 能读到内容吗 |
| --- | --- | --- |
| 原生 Win32 | 记事本、资源管理器 | ✅ 完整 |
| 浏览器 | Edge / Chrome | ✅ 完整（地址栏 + 页面正文 + 扩展名） |
| Chromium / Electron | WorkBuddy、VS Code、QQ NT、新版微信 | ❌ 只有一个空壳（`Chrome Legacy Window`） |
| 游戏 / 远程桌面 | — | ❌ 自绘界面，读不到 |

Electron 系默认**不暴露 accessibility tree**，得应用自己开启（Chromium 的
`--force-renderer-accessibility`）。所以对这类应用，**窗口标题是唯一可靠的信号**——
这也是为什么「整桌窗口快照」不是锦上添花，而是必需的兜底。

真正的内容兜底是 OCR（Screenpipe 同样走这一步），列为后续项。

## 一个具体的坑：根元素取错会抓到任务栏

第一版从 `FocusedElement` 向上找顶层窗口。焦点落在任务栏或开始菜单时，这条路径会
**一路爬到任务栏**，于是「WorkBuddy 窗口」抓回来的是一排「开始 / 搜索 / 任务视图」。

改成直接用前台窗口句柄 `AutomationElement.FromHandle(hwnd)` 取根元素，问题消失。
教训：**UIA 的树是整屏的，找错根就等于在看另一个窗口**。

## 隐私：常驻记录的第一性问题

全天候看着屏幕的东西，一旦漏了密码框就不是功能问题而是事故。三层防线：

**① 窗口 / 应用黑名单** —— 密码管理器、银行、支付、无痕窗口。
用子串匹配而不是正则：配置是给人写的，写错一个正则漏一整类，写错一个子串最多多记一条。

**② 敏感内容识别** —— API key、长 base64、银行卡号、身份证、私钥。
命中就**整条丢弃**，不做局部打码——打码后的残句照样泄露上下文。

**③ 记录时段** —— `active_hours: [9, 23]`，下班自动歇着。

**被拦下的事件完全不落盘**，连「几点用过什么应用」这样的骨架都不留：银行这类，
留下使用时刻本身就是泄露。

落盘点 `journal.record()` 会**再查一遍**——不指望上游一定查过。落盘是防线的最末端，
绕过它的路径早晚会出现，所以它自己得站得住。

## 中文检索：为什么要先做 bigram

FTS5 默认的 `unicode61` 分词器把中文**按单字切**。结果：搜「会议」会命中所有含
「会」或「议」的文本，等于没过滤。

所以存之前先把中文切成二元组：

```
「Q3 复盘会议纪要」 → q3 复盘 盘会 会议 议纪 纪要
```

搜「会议」→ 命中；搜「纪要」→ 命中；搜「会议纪要」→ 命中（两个 token 都中）。
英文照常按词切。

```
memory/journal.py   DesktopJournal
  record()       落库（含隐私终检）
  search()       按内容搜，支持应用过滤与时间下限
  day_summary()  今天用了什么、各停留多久
  purge_before() 按天数清理，常驻记录不能只涨不落
```

## 理解层：用 0.05 秒的小模型判断「他在干什么」

采集上来的只是原始文字。要知道「他在忙什么」，还得再判一层。这一层**不需要大模型**——
思路来自 **typesafe-computer-use**（853 stars，MIT）：用 OCR + 无障碍树喂给**小分类器**
决定下一步，只在真需要自由文本时才调前沿模型。

用的是手边的类 Jev 决策模型（`jev-playground` 的 Laya 多语言权重，643 MB，CPU 可跑）。
它的抽象很干净：

```
state（看到的内容） + questions（choice 多选 / score 打分 / noul 是非） → 结构化答案
```

于是问它三件事：**在做什么类型的活**（choice）、**多专注**（score）、**现在能不能打扰**（noul）。

### 加载为什么慢，以及怎么绕开

| 场景 | 耗时 |
| --- | --- |
| 冷启动（首次） | 55.3 s |
| 热启动（OS 文件缓存命中） | 7.4 s |
| **常驻后每次判断** | **0.05 s（直连）/ 0.38 s（HTTP）** |

瓶颈是**磁盘 IO**（615 MB 权重 + 33 MB tokenizer），不是模型初始化——缓存一命中就从
55 s 掉到 7.4 s。这直接决定了优化方向不是「换更小的模型」，而是「别重复加载」。

所以正确用法只有一种：**启动时加载一次，然后常驻**。每起一次新进程都要重付这份开销，
那样子这条路根本不可用。助手的做法是启动时把服务拉起来（`autostart`），
**加载期间用规则兜底顶着**，加载完自动切到模型——那几十秒用户感知不到。

三级后端按可用性自动降级，保证这个功能永远有输出：

1. `http` —— 本地 Jev 服务（需 jev-playground 的 server.py 常驻）
2. `rules` —— 纯关键词兜底（零依赖、零延迟），认不出来给 `other`

### 这一层带来什么

日报从「编辑器 43 分钟」升级成 **「写代码 3 小时、看资料 1.2 小时、开会 40 分钟」**。

还有个 `interruptible` 字段 —— 开会时标「别打扰」。助手以后要主动开口之前，先看一眼它。

## 两条读屏路线对比（实测数据）

### A. 系统 API 路线（本项目现用）

UIA 无障碍树 + Windows OCR + 322M 小分类器。**刻意不吃显卡。**

### B. 视觉模型路线（`understand/vlm.py` 已实现，未启用）

截图 → VLM 理解。吃显卡。

### 硬数据对比

| 维度 | A：UIA + OCR + 小分类器 | B：截图 + VLM（Qwen2.5-VL-7B） |
| --- | --- | --- |
| 读屏方式 | 系统无障碍树 + 系统 OCR | 整屏像素 → 视觉模型 |
| 单次延迟 | UIA 1.1 s / OCR 0.37 s / 分类 0.05–0.38 s | **2.3 s**（4060 图文问答）/ TTFT **5.2 s**（3050）|
| 冷启动 | 15.8 s（常驻后无感）| **~30 s 模型加载** |
| **显存** | **0** | **4.7–8 GB（吃满 8GB 卡，3050 标注 Tight fit、89% 占用）** |
| CPU | 只在窗口切换时动一下 | 推理时 32–58% |
| 磁盘 | 614 MB | 4.3 GB（Q4_K_M） |
| 文本准确度 | **精确**（读到的就是原文）| 可能认错字、可能幻觉 |
| 中文 | 精确 | 有识别误差 |
| 覆盖范围 | 有 accessibility 的应用；**Electron 系靠 OCR 补** | **任何像素能显示的**（含游戏、远程桌面、图表、图片内文字）|
| 理解深度 | 只做类型化判断（choice / score / noul）| **开放问答、能推理、能描述** |
| 隐私 | 全本地 | 本地可以；走云端则要上传截图 |
| 成本 | 0 | 本地 0 / 云端按 token |

### 怎么选：不是二选一，是分工

这正是 **typesafe-computer-use** 的打法——用便宜的路子扛常态，只在真正需要自由文本
或画面理解时才调重模型。落到这套感知系统：

```
常态（每次窗口切换）
  → A：UIA + OCR + 小分类器，打活动标签，约 1.5 s，零显存

按需（少数场景才触发 B）
  → 用户问「我刚才看的那张图里是什么」
  → 页面是图表 / 图片，文本层和 OCR 都读不出
  → 小分类器置信度低
```

**关于家里那张显卡的实话**：8GB 跑 7B VLM 是 tight fit，会吃满显存，
你同时开别的东西就难受了。更划算的是**云端 VLM**（硅基流动的 Qwen2.5-VL 有免费额度，
本项目 `vlm` 段已支持 OpenAI 兼容端点），按需调用、不占本地显存；
或者本地跑 **3B 级 VLM**（约 2–3 GB 显存），能力够用且不挤占资源。

## 现在能问什么

- 「**我今天干了什么**」→ 记了多少条、时段、各应用停留时长、出现次数
- 「**找一下我之前看的那个 Agent 记忆方案**」→ 按内容回忆，返回时间 + 应用 + 片段

两个工具走 `journal.today` / `journal.search`，意图层有对应的口语说法。
你不需要主动录入任何东西——这就是被动感知的意义：**平时它看着，需要时才被问起。**

## 与旧链路的关系

原来的 `capture/screen.py` + `understand/vlm.py`（截图 + VLM）保留着，作为兜底手段：
UIA 读不到内容的应用（游戏、远程桌面、部分自绘界面）才回去走截图那条路。
`pipeline.py` 的定时采集也保留，供 `main.py watch` 这类显式命令使用。
